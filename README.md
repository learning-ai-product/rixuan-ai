# 日选 AI · 出海 Listing 智能生成与合规风控

> 面向 TikTok Shop / 独立站卖家的中日双语 Listing 生成工具。内置合规风险分层与熔断降级机制，避免生成违反目标市场法规的内容。

## 项目背景

2026 年 6–8 月我作为 TikTok Shop 美区一级经销商运营，发现小卖家写一条多语言 Listing 平均要 2 小时，且对目标市场法规（如日本 PSE、欧盟 GPSR）缺少判断，容易踩雷。本项目从该痛点出发，用 Streamlit + DeepSeek API 做了一个可交互的 MVP。

## 当前功能

- 输入商品信息后，自动生成亚马逊日本站 / 其他市场风格的 Listing
- 根据「目标市场 + 品类」输出高 / 中 / 低三档风险等级
- 命中高风险时熔断，提示人工复核；中风险抽检；低风险直通
- 失败时输出兜底卖点模板，而不是报错页
- 高频问题走本地缓存，降低 API 调用成本
- **法规查询 RAG**：基于本地法规语料的检索式问答，要求模型引用条款编号回答（见 `regulations/法规收集手册.md`）

## 运行方式

```bash
pip install -r requirements.txt
streamlit run app.py
```

## 密钥配置（重要）

代码里**没有写死任何 API Key**。本地开发时可在侧边栏输入；部署到 Streamlit Community Cloud 时，在 App 后台 `Settings → Secrets` 配置：

```toml
DEEPSEEK_API_KEY = "你的 DeepSeek API Key"
```

## RAG 设计：为什么用 BM25 而不是向量库

法规检索和文档问答的目标不一样。文档问答追求"语义相近"，法规检索要求**能说清依据来自哪一条**——因为答案会直接进入 Listing 文案和合规提示，说不出依据的相似度是不可接受的。

所以这里的做法是：

- **切分**：一条法规要点 = 一个 chunk，不做二次切分（法规本身已是短条目）
- **召回**：BM25 关键词检索（jieba `lcut_for_search` 搜索引擎模式分词）
- **约束**：Prompt 要求模型必须引用条款编号回答

代价是同义改写召不回来（用户问"能不能打折卖"召不到"有利误认表示"），收益是每条结论都能追溯到原文出处。这个取舍对合规场景是划算的。

## 法规语料现状

`regulations/` 下 40 条，覆盖日本（PSE 制度 10 条 / 景品表示法体系 10 条）与欧盟（GPSR+GDPR 10 条 / CE 制度 10 条）。

**核对状态：9 / 40 条已官网核实**，其余为待核对草稿。进度表见 [`语料核对清单.md`](regulations/语料核对清单.md)。

核实过程中**修正了 2 处 AI 生成的实质错误**：

| 条目 | AI 原写 | 官方事实 |
|---|---|---|
| `JP-CAA-003` | ステマ規制自 2025-10-01 施行 | **2023-10-01** 施行 |
| `JP-PSE-002` | 事业届出须在**开工前**提交 | **事业开始之日起 30 日内**（法第3条） |

第 2 处是方向性错误——「先批再干」vs「先干后报」，会让卖家误判合规时序。已核实的 9 条 `verified=true`，`source` 列写入具体官方文件链接。

## 已知局限

- 法规语料未逐条核对官网原文（见上），且仅覆盖日本与欧盟两个市场
- 同义改写召回率低（BM25 的固有局限，见上节取舍说明）
- 品类维度稀疏：`beauty` / `baby` 两类在风险表里权重最高（2 / 3），但语料暂无对应法规条目
- 模型输出需人工最终审核，不可替代专业法务/合规判断
